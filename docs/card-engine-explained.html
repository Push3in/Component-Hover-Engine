Card Hover Engine · a guide for designers

Inside the Card Hover Engine

How five cards from your Figma file fan out along a curve, size themselves to your screen, grow when you hover and get knocked around when you swipe through them. Every idea here has a live specimen you can touch, built with the same maths as your project.

Every time your mouse moves, the code draws a line from where it was to where it is, checks whether that line crossed a card, and if so pushes that card the same way (harder for faster swipes, with spin for off-centre hits). Then a spring pulls it back home. Each card does this on its own.

Part 1 · Structure

Frames inside frames

A web page has three layers of work. Structure says what exists and what sits inside what, like your Layers panel. Style says how it looks, like the Design panel. Behaviour says what happens when you interact, like the Prototype tab.

Your page is a stack of nested frames. The outer .container has 40px padding. Inside it, .ribbon lines the cards up in a row and decides their size. Each card sits in its own .slot, which holds its place in the fan. Inside the slot is .card, the part that grows and gets pushed, and inside that is the design itself: Weather, Player, Status, Audience or Quote. A className is just a layer name; the CSS file styles anything with that name.

The specimen shows one card to keep it simple. In your project the ribbon holds five.

Part 2 · Style

One number sizes every card

The ribbon sets a variable called --card-scale. Anything starting with -- is a value you name yourself, and every layer inside the ribbon inherits it, the way a Figma variable feeds every layer that uses it. At 1 the cards are exactly their Figma size.

Each card turns that number into a text size: 16px × scale. Everything else inside is measured in em, which means "a multiple of my text size", so 1em is 16 Figma pixels. Padding, corners, gaps, icons and shadows all follow the text. Drag the dial to see the chain. In your project you don't set this number by hand any more; Part 3 shows how it's worked out from your screen.

Part 3 · Fit to screen

Big monitor, big cards

The browser always knows the size of its page area: window.innerWidth and window.innerHeight. A small helper, useFitScale.js, reads those two numbers and picks the --card-scale that makes the fanned row fill a share of the window. That share is the fill dial: 0.75 means 75%.

First it needs the row's size at Figma size. Width is the five card widths added up (1204px) minus the four overlaps (4 × 60px), so 964px. Height is the tallest card, Status at 188px, plus how far the outer cards drop for the curve (48px), so 236px. Then it's one division per side, and the smaller answer wins, like "Scale to fit" in Figma: grow until you hit the first edge, then stop.

The browser fires a resize event whenever the page area changes: dragging the window edge, maximising, moving it to another monitor, or zooming. The helper listens for it and redoes the maths, so the cards follow straight away.

Part 4 · The fan

Squeezed together, bent along a curve

Each card knows its offset: how many steps it is from the middle card. Status is the middle, so it's 0. Player and Audience are −1 and 1. Weather and Quote are −2 and 2. Three dials turn that one number into the fan:

Overlap pulls every card except the first to the left so it overlaps its neighbour, using a negative margin. Angle tilts each card by offset × angle, so the outer cards tilt twice as much as the inner ones and the two sides lean opposite ways. Curve drops each card by offset × offset × curve. Squaring the offset is what makes it a curve rather than a slope: the inner cards drop 12px, the outer ones 48px, and both sides drop the same because a negative times a negative is positive.

The middle card sits on top, and each card further out sits underneath the one beside it. That's the stacking order (z-index): 50 minus how far out the card is.

The tilt and drop are transforms, so the layout still measures each card as if it were flat. That's why the outer cards poke out past the bottom of .container when you turn on the skeleton. Every card also has a soft drop shadow (0 1px 3px at 6% and 0 8px 24px at 10% black) so the overlaps read as layers.

Part 5 · Behaviour

Hover grow

Each card listens for the pointer arriving and leaving. Those two moments flip a yes/no switch called hovered, which React remembers, like switching a component variant. Every card has its own switch, so only the one under your pointer reacts.

When hovered is yes, the card's target size becomes the hover scale (1.2). Motion then moves a second variable, --hover-scale, toward that target a little every frame, about 60 times a second, using a spring. That variable sits inside the font-size formula above, so the card really resizes and its neighbours slide apart to make room, like a hug-contents frame in Figma. It keeps its place in the stacking order, so a hovered outer card grows partly under the card beside it.

Part 6 · Step by step

What happens on every mouse move

01

Listen to the whole window

The browser reports the mouse every 8–16 milliseconds: where it is (x, y) and when. The code listens on the whole page, not just the card, so a swipe that starts outside still counts as it passes through.

window.addEventListener('pointermove', handlePointerMove);
02

Two dots become a line

The browser only hands over dots. A fast swipe can jump 60px between them, skipping right over the card. So the code remembers the previous dot and joins it to the current one. That line is "the swipe".

const prev = last;   ← where the mouse was last time
last = now;          ← remember this spot for next time
03

Ignore pauses

If more than 0.12 seconds passed between two dots, the mouse stopped. A line between them isn't a real swipe, so nothing happens. return means "stop here".

const MAX_GAP = 0.12;          // seconds
if (dt > MAX_GAP) return;
04

Did the line cross the card?

A small piece of geometry, called Liang–Barsky, answers one yes/no question: does this line pass through this rectangle? That's why a quick swipe still hits even when no dot lands inside the card.

const rect = card.getBoundingClientRect();      ← the card's box on screen
if (!segmentHitsRect(prev, now, rect)) return;  ← missed? stop.
05

How fast was the swipe?

Speed is distance divided by time, like km/h but in pixels per second. A gentle swipe is around 300 px/s; a flick can be 3000 px/s.

const dx = now.x - prev.x;      ← how far sideways
const dy = now.y - prev.y;      ← how far up or down
const speed = length / dt;      ← pixels per second
06

Kick in the swipe's direction

The card's new speed is whatever speed it already had plus the swipe's speed × strength. Direction comes for free: a rightward swipe has a positive dx, so the kick is rightward.

Strength (0.18) is how much of your swipe reaches the card, a bit like how heavy it feels. At 0.18, a 2000 px/s flick gives the card 360 px/s. Keeping the speed it already had is momentum: hit it again mid-wobble and the pushes add up.

x.getVelocity() + (dx / dt) * strength
07

Spin from an off-centre hit

Push a door near the hinge and it barely moves; push the far edge and it swings. The code finds the point on your swipe closest to the card's centre and measures how far off-centre it is. Physicists call this torque: 0 is dead centre, ±1 is the edge, and the sign gives the direction.

torque * speed * strength * spin * 0.2   // degrees per second

The 0.2 is a scaling number picked so the spin looks right with the default dials.

08

Safety limits

Without caps, a wild flick could fling the card off screen or spin it like a fan. The push speed stops at 2400 px/s (the same cap graphicalui uses) and the spin at 360°/s.

const MAX_SPEED = 2400;   // px per second
const MAX_SPIN = 360;     // degrees per second
09

Spring back home

One line per direction tells Motion: "go to 0, which is home, but start already moving at this speed." Picture the card on a rubber band pinned to its home spot. The kick stretches the band, the band pulls back, the card overshoots a little, then settles.

animate(x, 0, { ...home, velocity: vx });
animate(y, 0, { ...home, velocity: vy });
animate(rotate, 0, { ...home, velocity: vr });

These three values become a transform. A transform moves how the card is drawn without changing its place in the layout, like a layer set to ignore auto layout. That's why a push never shoves the neighbouring cards around, while hover grow does.

Part 7 · Springs

The rubber band, drawn over time

A spring can be described two ways, and DialKit's spring editor switches between them. Time mode uses duration (roughly how long it takes) and bounce (0 is no overshoot; higher is wobblier). Physics mode uses stiffness (how strong the band is), damping (friction) and mass (how heavy the card is). They're interchangeable: any duration and bounce equal some stiffness and damping.

The graph shows the card's sideways position after a 600 px/s kick. Change the dials and watch the curve.

The bug we hit

When the card only grew and never moved, two things were wrong. The first was Motion: in Time mode, if the start and the end are the same place, it ignores the starting speed. A push is exactly that case (home to home, with a kick), so Motion thought there was nothing to do. That's the flat pink line.

The fix converts your Time settings into the equivalent Physics settings before every kick, using the same formula Motion and DialKit use. The numbers above the graph are that conversion, live. The second problem was your Mac's Reduce motion setting, which the push now ignores, as you asked.

function toPhysicsSpring(spring) {
  const root = (2 * Math.PI) / (visualDuration * 1.2);
  const stiffness = root * root;
  const damping = 2 * (1 - bounce) * Math.sqrt(stiffness);
  return { type: 'spring', stiffness, damping, mass: 1 };
}

Part 9 · Words

Glossary

Component
A reusable building block, like WeatherCard or Card. Same idea as a Figma component.
State
A value React remembers and redraws for when it changes, like hovered.
Prop
A setting passed into a component, like a component property in Figma.
CSS variable
A named value starting with -- that inner layers inherit.
em
A unit meaning "× my text size".
Viewport
The visible page area of the browser window, without the tabs and address bar.
Resize event
A message the browser sends whenever the viewport changes size.
Offset
How many steps a card is from the middle card: −2, −1, 0, 1, 2.
Stacking order
Which card is drawn on top where they overlap (z-index), like layer order in Figma.
Transform
Moves, rotates or scales how something is drawn without affecting layout.
Event listener
Code that waits for something to happen, like a mouse move, and then runs.
Velocity
Speed with a direction, in pixels per second.
Momentum
Speed the card already has, carried forward. New pushes add to it.
Torque
An off-centre push that makes something spin.
Spring
An animation that behaves like a rubber band: overshoot, then settle.
Motion value
A number Motion updates every frame without redrawing all of React, which keeps it smooth.
